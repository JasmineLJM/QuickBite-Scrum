# Sprint Retrospective Evidence 

## Part H — Sprint Retrospective

### Participant: All four team members 
### Date: October 8, 2026 
### Sprint: Final retrospective covering Sprint 1-3
### Location: Zoom

## What went well? 
The team successfully developed the QuickBite Restaurant Pickup Platform through three Sprints. 

Sprint 1 focused on the core customer ordering workflow, Sprint 2 added restaurant order management and input validation, and Sprint 3 implemented restaurant pause controls. 

The team responded to stakeholder feedback by updating the Product Backlog and implementing the agreed pause feature.

GitHub branches, commits, and pull requests helped the team organize development work and integrate changes. 


## What did not go well? 
During development and testing, the team encountered some issues with input validation. For example, the Place Order button was initially disabled when the cart was empty, preventing the expected error message from appearing. Additional debugging and code changes were needed to correct this behavior. 

The team also identified an incomplete Product Backlog Item (PBI#10 - Review Order). Although customers could view order information after order submission, the application did not provide a order summary before placing an order. This item remained in the Product Backlog for future development.

## What slowed the team down? 
The team spent additional time to understand GitHub workflows, including creating branches, submitting pull requests, and merging changes. 

Requirement changes also required the team to revise acceptance criteria, Sprint planning, and supporting documentation so that they reflected the implemented software correctly. 

## What helped collaboration? 
Using the shared GitHub repository and project board helped team members to track responsibilities and development progress. All completed Pull requests made code changes and updates visible, and supported integration.

## Did Definition of Done work effectively? 
The Definition of Done worked effectively, it helped the team focus on working functionality and testing instead of just completing the code changes. The team also verified that the implemented features met their acceptance criteria before marking completed PBIs as Done.

## What should the team change in the next Sprint? 
### Improvement Action 1 - Improve Cross-Browser Compatibility Testing 
In the next Sprint, the team will test the main customer and restaurant workflows in Google Chrome, Safari, and Microsoft Edge before the Sprint Review. Any browser-specific issues will be recorded in GitHub Issues and assigned to a developer for investigation. 

### Improvement Action 2 - Improve Task Coordination and GitHub Workflow 
At the beginning of the next Sprint, the team will assign each development task to a specific team member and identify any dependencies between tasks. Developers will use seperate branches for their changes and create pull requests for integration. The team will review GitHub Project status during Daily Scrums to identify blockers earlier.

## Retrospective Outcome 
The retrospective highlighted the team's progress in delivering working software, adapting to changing requirements, and collabrating through GitHub. 

The team identified two improvements for future Sprints: testing across multiple browsers earlier and improving tasks coordination through clearer assignements and regular GitHub Project updates.
